# Codebase Notes

Also follow the global `AGENTS.md` instructions, when the file exists. This file adds the notes of this project.

## Commits

Never commit the owner’s uncommitted changes, especially in `content/`. They are often about app features that are not released yet, like new actions in `content/apps/actions/index.md`. Before you commit, list the uncommitted changes that you did not make: run `git diff` and check `git stash list`, as the owner may have stashed them. When you and the owner changed the same file, stage only your hunks (for example with `git apply --cached` and a patch of your hunks), and check with `git diff` that only the owner’s changes stay uncommitted. Do not run git commands that change the index or the working tree while another agent stages a commit.

Some changes to app pages are in `git stash`, as the app update that they are about is not published yet. Before you suggest or make a change to the content of an app page, check the recent stashes (`git stash list` and `git stash show -p stash@{n}`), so the change does not repeat or contradict them. A content file, `content/site.soml`, or a script of the site with a git conflict marker, like `<<<<<<< Updated upstream` after `git stash pop`, is a content error at the line of the marker.

## Browsers

The site targets only modern browsers (the latest Safari, Chrome, and Firefox). Use the latest CSS, HTML, and JavaScript features and syntax freely, like relative colors (`oklch(from …)`) and `sibling-index()`, without fallbacks for older browsers.

## Modern APIs before speed

Prefer modern syntax and APIs to the fastest ones. For example, use Swift `Regex` and regex literals, not `NSRegularExpression`, even where `NSRegularExpression` is faster. The build is fast enough, so do not trade readable, modern code for performance unless something is too slow to use.

Swift makes the `Regex` of a literal again, and compiles its program again, each time the code runs, so a regex that runs often, like in a loop or for each page, is stored in a `static let` or a file-level `let`. A stored regex is `nonisolated(unsafe)`: `Regex` is not `Sendable`, but it is immutable and compiles its program once, thread-safely.

## Numbers and lists in text

Text that the build makes is in the language of the site (`Locale.site`), whatever the locale of the Mac. For these four cases, use the shared styles in `Sources/SiteKit/Utilities.swift`, not a new `.locale(.site)` chain (other formats, like a rating, a percentage, or a price, keep their own chain): `count.formatted(.siteNumber)` for a whole number, which has a thousands separator only from five digits, like “1234” and “40,000”, `count.formatted(counting: "app")` for a count with its noun, `size.formatted(.siteFileSize)` for the size of a file, and `names.formattedList(.and)` or `names.formattedList(.or)` for a list of strings in a sentence.

## Image formats

Do not use AVIF. Keep the images PNG and JPEG. The build makes a JPEG XL copy of the icon and the screenshots of each app (`JPEGXLCopy`): a PNG at quality 90, which looks the same and is much smaller, and a JPEG wrapped losslessly. The pages offer it in a `<picture>` when it is smaller. It needs `cjxl` (`brew install jpeg-xl`), and the copies are cached in `.cache/jpeg-xl`. The places that need a common format keep the PNG or JPEG, like the favicon, the social card, and the sitemap. An image with the data of the other format, like a JPEG that is named `icon.png`, is a content error. A HEIC image in the text, like a photo from an iPhone, is a content error too, as only Safari shows it.

## Assets

A page is a Markdown file, or a directory with an `index.md` (a page bundle) when it has files of its own, like images. The files of a page bundle are published next to its page: `content/apps/dato/icon.png` at `/dato/icon.png`, `content/blog/post/image.png` at `/blog/post/image.png`, and `content/pages/about/lego.jpg` at `/about/lego.jpg` (`Project.site(root:)`), but only when the site publishes the page, so a draft app, post, or guide (`isDraft: true`) does not publish its files. Only the files directly next to the `index.md` are published, not the files in its subdirectories. The folder of an app or a post has one Markdown file, its `index.md`: another one, like `draft.md` or `index copy.md`, is a content error, and `website check` warns about a folder with files but no Markdown file. An app's icon, screenshots (`screenshot1.png/jpg`), and videos (`video1.mp4`) are files of its page bundle. Another name that starts with `screenshot` or `video`, like `screenshot1 copy.jpg` from a copy in Finder, is a content error, as the page would show it as one more item. Another format or a capital letter, like `screenshot7.heic`, `video1.mov`, or `Screenshot7.jpg`, is a content error too, as the page would silently leave the file out. Each video has a poster next to it, like `video1-poster.jpg` for `video1.mp4` (a content error without it). The originals of the videos, and how to encode a new video and make its poster, are in `~/dev/project-extras/Website`.

Link to them relatively in the Markdown, like `[photo](lego.jpg)`. A relative link with a file extension to a file that does not exist is a build error. A link to the `.html` file of a page, like `/dato.html` for `/dato`, is a broken link too, as it is a second URL of the page. Files that many pages use, or that other sites link to, like the logos in `public/assets/thanks`, go in `public/`, as their URLs must not change.

## App categories

The chips of the apps page and the category pages, like `/apps/menu-bar`, are the cases of `AppCategory`, in the order of the cases. Most categories come from the facts of an app, like its platforms or `isMenuBarApp`. A category that no fact gives is hand-picked: the `categories` frontmatter of an app has it, like `categories: ['clock-and-calendar']`, and the hand-picked cases are in `HandPickedCategory` (`shortcuts`, `clock-and-calendar`, `ai`, `notes`, `files`, and `browsers`). Give a hand-picked category only to apps that are released and not archived. “You Might Also Like” on an app page shows the apps of the `relatedApps` frontmatter of the app first, in their order, like `relatedApps: ['menu-bar-spacing']`, and then prefers the apps of the same hand-picked category (`App.relatedApps(from:on:)`). Name a related app there, not in a tip like “You may also like my … app”, as the cards already show its name, icon, subtitle, and price. A slug in `relatedApps` that is not an app, an app that is archived, unlisted, or has no page of its own, the app itself, or more than 4 slugs, is a content error at its line. A category page shows the featured apps that it has first, in the order of the apps page that day (`SiteContent.dailyFeaturedApps`), and then the others, newest first. The chips (`AppCategory.chips`) are the main categories. The others, like `clock-and-calendar`, `ai`, `notes`, `files`, and `browsers`, are only in the “…” menu after the chips (`AppCategory.menuCategories`), so the row of chips stays short. The Mac apps are almost all the apps, so “Mac” is not a chip either. The menu and the list at the end of the apps page put the platforms and the prices in a group of their own, “Platforms & Price” (`AppCategory.isPlatformOrPrice`), after the categories of what the apps do.

## Guides

Every guide has a `topic`, one of `Guide.Topic`, like `topic: 'menu-bar'`, which groups it on the list of guides, and a guide can show a screenshot of its first app after the steps, like `screenshot: {number: 1, description: 'The result in the menu bar'}`, where the number is the one in the file name of the screenshot, like `2` for `screenshot2.jpg`. The page shows the name of the app and the description below the screenshot, like “Zone Bar: The time in five cities in a menu below the menu bar”, as the section above it is not always about the app, or only the description when it already names the app, like “Velja asks which browser to open a link in”. The caption is the text of the image for screen readers, so the image has no alternative text. The lists of guides show the titles without “How to” (`Guide.task`), as the title of the list already says that the items are guides. An unknown slug, a slug given twice, or an app that is archived, unlisted, or has no page of its own is a content error, like for the featured apps of `content/site.soml`. A guide starts with `@QuickAnswer` (the app and the built-in way), which links to the first app, has the steps in `@Steps`, and has an honest `## Without an app` section with text. A sentence of the short answer about the built-in way starts with a link to that section, `[Without an app](#without-an-app),`, as the section is far down, after the box to get the app. The headings of guides and blog posts have a link that copies the URL of their section, like on app pages (`addsHeadingAnchors`), and so do the section titles with an ID that Swift renders (`Section`), like “macOS 12” of Older Versions. The heading of the section of an app, like “With Dato”, shows the small icon of the app before its text (`addAppHeadingIcons(project:iconCopies:apps:)`), so the sections of the apps look different from “Without an app”. The steps below “Without an app” are gray, not in the color of the app, as they need no app. Each step of a `@Steps` list below a heading has an ID from the heading and its number, like `with-dato-step-2`, and its number is a link that copies the URL of the step (`addingStepLinks(headingID:)`). Limitation: a second `@Steps` list below the same heading has no IDs. The build checks this shape, and a guide without it is a content error with its line (`Guide.shapeErrors`). Below the title, the page shows who wrote the guide: the small photo of `Site.author`, “By Sindre Sorhus” with a link to `/about`, and all the apps of the guide, like “who makes the Folder Peek app” or “who makes the Menu Bar Calendar and Dato apps”. The page shows the box to get the first app (`AppCallToAction`, like at the end of an app page) before `## Without an app`, so the built-in way stays the last word. Link to a guide by its slug, in any content file: `<guide:open-files-with-enter-finder-mac>` after a feature or an answer is a small “Guide ›” tag (`MarkdownDocument.Options.linkTags`), like after a feature of Supercharge, and `[the guide](guide:open-files-with-enter-finder-mac#steps)` is a link in a sentence. A slug that is not a guide is a content error with the slug that is closest (`MarkdownFile.resolvingLink`), so a guide that gets another slug breaks the build at each link to it, and `website check` warns about a link to a guide by its path, like `/guides/…` or `…/guides/….md`. The tag shows “Guide”, and its name for screen readers and its text in the Markdown copies is the title of its guide without “How to”, like “Guide: Open Files with Enter in Finder on Mac”, which the renderer reads from the frontmatter of the guide file (`Guide.task(slug:project:)`), as the documents render before the guides are loaded. The tags of links are in one place (`[String: MarkdownDocument.LinkTag].site(project:)`), and every rewrite of Markdown for readers outside the site uses them through `PlainMarkdownRewriter.site(project:linkDestination:blockDirective:)`, so no copy has a tag as raw text. Limitation: the name of a “Details” tag is “Details”, as the headings of the page are not known when its link renders. Link to an app page by its site path, like `[Supercharge](/supercharge)` or `[Dato](/dato#faq)`, not by its content file: `website check` warns about a link like `../apps/supercharge/index.md`, with the site path to write. The sites are the cases of `SourceSite`, and a tag to another site is a content error. A link in a sentence, like “(Apple’s instructions)”, and a link at the start of a paragraph stay links. ## Link previews

A link in prose shows a small preview of what it goes to when the pointer of a mouse rests on it (`LinkPreview`, `site.js`): the page of an app, a question of an FAQ (the question and the start of its answer: its paragraphs and list items, without the labels in bold), a guide (the icon of its first app, its title, and its short answer, the `description`), or a shared shortcut on iCloud (its icon and its name). The preview starts where the link starts, below it, or where there is space. The build writes what each preview shows to `/link-previews.json` (`LinkPreview.data(for:)`), by the link, and the script only looks the link up, so a new kind of preview is new data, not new script. The script gets the path of the file from the template of the preview (`LinkPreview.Hooks.data`), so the path is only in Swift (`LinkPreview.dataPath`). Only the questions and the guides that a link in the content goes to are in the file, as the lists of guides show no preview. Text outside `Prose` gets previews with the hook `LinkPreview.Hooks.linkPreviews`, and a box or a link that already shows the thing, like the card of a shortcut, has `LinkPreview.Hooks.noLinkPreview`. The link of a section that copies its URL (`data-copy-link`) shows no preview either.

A link to a shared shortcut (`https://www.icloud.com/shortcuts/…`) on an app page gets the name and the icon of the shortcut from iCloud (`Shortcut`). A link that is alone in its paragraph or list item is a card (`ShortcutCard`), and so is a link at the start of a list item, where the text after it is a note below the card, like `- [Presentation Mode](…): Hides the desktop icons.`. A link in a sentence shows the preview, and the Markdown copy of the page has the name after the link when the text of the link does not have it.

The first link to the page of one of my apps in the text of an app page, a guide, or a page of `content/pages` shows the small icon of the app before its name (`addAppLinkIcons(project:iconCopies:excluding:)` in `MarkdownOptions.swift`, `linkIcon` of the options of the renderer), so a reader sees that the text names an app of mine. The text renders while the apps load, so the build makes the JPEG XL copies of the app icons first (`App.iconJPEGXLCopies(project:)`), and the icon has its copy like every other app icon. The icon stays on one line with the first word of the link. A link to the product of an app on Gumroad, like `https://sindresorhus.gumroad.com/l/supercharge/BLACKFRIDAY` in the list of a sale, gets the icon of the app too, as the IDs of the products are the slugs of the apps. The app of an app page and the apps of a guide get no icon, as the page already shows them, but the heading of the section of each app of a guide, like “With Dato”, has its icon (see “Guides”). A link that starts a list item with a `:: ` line, like `- [One Thing](/one-thing)` with `:: Control the menu bar` below it, always gets its icon, also when the text named the app before, as the app is the subject of the item, and the icons of such a list make a column (only the list of apps at the end of the page of Actions now). On an app page, the first link in a sentence to a shared shortcut that the build loaded shows the icon of the shortcut too (`addShortcutLinkIcons(_:)`), as the shortcuts are only loaded for app pages. Blog posts, frontmatter texts, footnotes, and notes have no icons. The “Compared with” chips of an app page show the icon of an app of mine too (`LabeledLink.iconPath`).

## Site search

The header has a round button with a magnifying glass, “Search” for screen readers, which opens the search of the whole site (`SiteSearch`): a dialog with one field, and the results in groups: Apps (the archived apps last), Pages (the pages of the site with their `searchKeywords`, and the release notes), Guides (also by the words of their short answer), Sections (the headings of the app pages outside the FAQ and the tips, and the shared shortcuts), Questions (of the apps and of the general FAQ, with the start of the answer), Tips, Posts, and Open Source (`content/open-source.soml` without the apps). A group shows 5 results and a “Show N More” row. Each result has the icon of its app, or a symbol of its group. Before the visitor types, the dialog shows the featured apps and links to all apps, the guides, and the FAQ (`start` of the index). The results of the page that is open come first in their group. When the first result only matches by words, like an app by its subtitle, a title of a later group with the whole query is first, as the “Top Hit”, so Return opens it. A word of the query of 5 or more letters that is not a word of the index, another form of one, or the start of one, is corrected to the closest word of the index, like “calendar” for “calender”, and the dialog says so. Only a word that the query has as it is gets a correction, so the text of the correction shows it. A correction is kept only when the corrected query matches, and else the query is searched as it is, so “remind me to drink water” does not show the results for “drink later”. Limitation: a name that is not on the site, like “bartender”, can be corrected to a word of the site. When nothing matches, the dialog shows the app with the closest name, like Gifski for “gifksi”, or a link to the feedback page, and after 2 seconds GoatCounter counts the query as an event (“No search results”), once for each query, which the privacy page says. The site is a search engine of the browser (`/opensearch.xml`), and `/?q=dato` opens the search with the query. The “Help” column of the footer starts with a “Search” button, and the FAQ of an app with 20 or more questions has a “Search Questions” chip, which opens the search with the name of the app (`SiteSearch.OpenButton`). Command+K or Control+K and the `/` key open it too, but not while the focus is in a field, where the keys edit the text. The Down Arrow and Up Arrow keys move the focus through the results, and Return in the field opens the first one. Escape closes the dialog in one press, also with text in the field, where a search field would first only clear the text, and the text stays for the next open. On phones, the button is next to the menu button, and from tablets, after the links (`SiteHeader.Styles.top` is `display: contents` there). While the bar of an app replaces the site navigation, the button is hidden with it, and the keys still open the search. Without JavaScript, the button is hidden. The build writes the index to `/search.json` (`SiteSearch.indexPath`, only in Swift, in the `config` of the element), which the script loads when the dialog opens the first time. An entry matches when its title has the whole query at the start of a word, like “ai” for AI Actions, or when each word of the query is a word of the entry, another form of it, or the start of it. A word of the query of 5 or more letters that is not in the index is the closest word of the index, like “calendar” for “calender”, and a note above the results says “Showing results for “calendar”.”, but not a word that starts with that word, like “photosh”, which the visitor is still typing. Spaces, hyphens, underscores, periods, and slashes are the same in the query and the titles, like “p limit” for p-limit, and the index has a name with a hyphen or a short part as one word too (`Entry.joinedWords(in:)`), like “wifi” and “vscode”, and the script joins these names in a title the same way, so “wifi” ranks “Wi-Fi” in a title like a plain word. A question of the general FAQ only needs the words of the query that are not the name of an app, like “supercharge refund”. A guide is also found by the names of the commands of its `console` and `sh` blocks (`CodeBlock.commandNames`), like “sips”, and each macOS version of Older Versions is a section, like “Older Versions for macOS 15”. The words of the query are bold in the titles and the details. The word rules are the ones of the related help of the feedback page (`SuggestedQuestion`, see “FAQ Suggestions on /feedback”): the index has the words of each entry, and the stopwords, the patterns, and the forms of the words, and both scripts use `/scripts/words.js`, so there is one matcher of words. A question that many apps have with the same answer, like a shared question, is in the index once, with the first app that has it. A question with the own answer of an app, like the localization question of Dato, is there for each app.

## Motion

Keep motion to a minimum in the content. Small transitions that help to understand a change, like a hover color or a menu that fades in, are fine. Do not add scroll animations, elements that move into view, parallax, or animations of the content itself, like text or cards that move by themselves.

Subtle background animations are fine, like the nebula of the home page, the drifting blobs of the contact page, or a slow glassy background behind a page header. They must be calm and slow, stay behind the content, show a still frame when the visitor prefers reduced motion, and pause when they are off screen or the tab is hidden. The galaxy of the home page and the glass of the apps page are the exceptions: with reduced motion, they are not started, and the page shows its plain background, or for the apps page, the still gradient that the page shows before the script runs. The home page also keeps the animated gradient of the name and the rotating ring in dark mode, as it is the playful page of the site.

The `animation()` style modifier does this by default: it writes the animation in `@media (prefers-reduced-motion: no-preference)`, so with reduced motion the element shows its style without the animation. Make that style the still frame, like the end of a fade in, and do not wrap the animation in `.media(.allowsMotion)` or stop it with `.reducedMotion { $0.noAnimation() }`. Hide a decoration that only makes sense while it moves, with `.reducedMotion { $0.hidden() }`. Only an animation that carries meaning and hardly moves runs with reduced motion too (`isEssential: true`), like the highlight of the section that a link points to. Scroll-driven animations (`animation(_:timeline:range:)`) follow the scrolling of the visitor, so they also run. Transitions and animations in scripts (`element.animate()`) are not covered: guard them yourself where they move things.

Read the reduced motion setting once, when the page loads. Do not handle a change of the setting while the page is open.

## Styles

A style that only one element has goes on the element itself, like a modifier in SwiftUI: `.style { $0.padding(.rootEm(1)) }`, or `.vstack(spacing:)` and `.hstack(…)` for a stack (`ElementStyle`). Its class is the name of the file and a hash, and the page collects its rule in the `elements` layer, after the components, so it wins over the styles of its component. Use a case in the `Styles` (a `StyleSet`) of the component for a look that more than one element has, for variants, and for a style that another selector refers to, like a parent that changes a child while it is hovered, as nothing can refer to a hashed class. A parent sets the space around a child component where it uses it, like `PressQuotes(…).style { $0.margin(.top, .rootEm(7)) }`, not with `.children(X.Styles.root.selector)`, so the child declares the tag of its root, like `var body: some HTML<HTMLTag.section>`. Never use inline styles or `<style>` in content. A value of the build, like the accent of an app or the size of a screenshot, is a custom property in a style of the element, like `.tint(color)` or `.style { $0.setting(Color.accent, to: color) }`, so no page has a `style` attribute (a test checks it). Before adding a style, reuse a component or a style that already exists, like `VisuallyHidden` for text that is only in the HTML, or a modifier like `.buttonStyle(.gradient)`.

When you simplify or remove duplicate code, do not remove style modifiers and other generally useful modifiers and utilities (in SiteKit or `Theme.swift`), even if nothing uses them now. They may be needed later. Only remove code that is specific to a feature that was removed.

Use full words in names, also for CSS units and keywords, like `.pixels(1)`, not `.px(1)`. Put the CSS keyword in the doc comment, like “(`px` in CSS)”. A length always has a unit, like `.padding(.pixels(1))` or `.gap(.rootEm(0.5))`: use `.zero` for a unitless zero. `Length` does not accept integer literals, so `.padding(1)` is a compiler error.

The “More Posts” list below a blog post is faded (`opacity(0.8)`) on purpose, so it does not draw attention from the post. Keep the fade, even though it gives its gray text less contrast, and do not replace it with another quiet look, like smaller post titles.

## Keyboard focus

The site has no focus rings, not even the ones of the browser (`SiteLayout`). Every focusable element must still show keyboard focus, often with the same look as under the pointer (`.hoverOrFocusVisible { … }`), never with an outline: a fill or a border for a control, a pill, or a card (`hoverFill(_:color:)` in `Theme.swift`), and a color or an underline for a link in text, like the links of the footer (`hoverColor(_:)`) and of the prose. A link or a button whose color cannot change, like the site name, which already has the strongest text color, or the dots of `AppMedia`, gets a round card fill on focus (`focusFill()` in `Theme.swift`). A current item (`aria-current`) already has a fill, so it shows focus with a thin edge instead: `.current { $0.focusVisible { $0.shadow(.edge(.secondaryText)) } }`, which `currentFill(_:)` in `Theme.swift` does, like for `navigationPill()`. A text field shows focus on its border, with a `focusRing` that covers the border (`FormField`): the only outline outside the 1999 page.

## Block directives

Content files can use the block directives in `Sources/Website/Components/MarkdownOptions.swift`, like `@Feature(title: "…") { … }` and `@Tips { … }`. Prefer one of them to raw HTML in content, and use Markdown links, not raw `<a>` tags, as a link inside one would be a nested link. Each has a sample in the gallery (`GalleryPage`), and the styles of each are a style set. Markdown renders before the pages, so a document collects the styles that its directives use, and the page adds them when it shows the document. So show a document with `document.content` (or `Prose(markdown:)`), not with `document.html`, which leaves its styles out. A test checks that every class on a page has a rule.

The names of the directives are the cases of `BlockDirectiveName`, which gives each its renderer. The arguments of a directive are a `@Frontmatter` struct, like `DetailsArguments`. Code that reads the Markdown tree, like a check of the content or `llms-full.txt`, decodes them with the same type as the renderer (`directive.arguments(as: DetailsArguments.self)`), not as strings, finds the directives also inside another directive with `document.blockDirectives`, and compares their names as cases (`directive.siteName == .details`).

- `@Cards { - … }`: a list as cards that flow through two columns from tablets. The text of each item is the title of its card, and a nested list is smaller text below it. Like the lists of the about page. A card that is only a link, also with tags after it, like `- [Random color](https://www.color.pizza)` of Plash, is a link card (`LinkCard`): the whole card is the link, without an underline, with “↗” after a link to another site and “→” after a page of the site.
- `@Steps { 1. … }`: a numbered list as steps, with each number in a circle in the accent of the page and a line to the next. A nested list is smaller text below its item.
- `@Changelog { - 2014 }`: a list of years, each with a nested list of changes, like the release notes of an app. A change can start with its kind, like `Added: Awesome`, which becomes a badge: Added, Changed, Fixed, and Removed in their colors, or Deprecated in gray. Another kind is a content error, and so is a kind in another case, like `added:`, which would silently lose its badge. Like the life changelog of the about page.
- `@Feature(title: "…", label: "…") { … }`: a main feature of an app, as a section with a numbered title, like “01”, so a few main features stand out from the rest of the page. The optional `label` is the plain name of what the feature is about, like `label: "Calendar"`, which the line above the title shows after the number, like “01 · CALENDAR”, so the title can be about what the feature does for the visitor. On an app page, all or none of the `@Feature` sections have a `label`, as the two have another look (a content error), and `website check` warns about a title that has its label as whole words, like “FINDER” above “Cut and paste files in Finder”, but not “AI” above a title with “Email”.
The build generates the trial and non-App Store download cards from the `trial` and `nonAppStoreVersion` frontmatter. They are typed components, not block directives. The trial section goes before the first level-2 heading, and the non-App Store section comes after the content, above older versions, so the downloads go from the newest version to the oldest. On the app page, the “Free Trial” buttons of the hero and of the box to get the app open the same trial card in a popover over the page (`AppHero.trialDialogID`), as the section can be far down. The popover covers the requirement of the hero, so its card shows the requirement of the app next to its button (`AppListing.trialCard`), only for macOS when the trial is a download. In a guide, the button links to the trial section of the app page, and a guide about the app on the iPhone only (`topic: 'iphone'`, `Guide.isAboutIPhoneOnly`) leaves it out when the trial is a download, as that is the Mac app, and its box to get the app names only the platforms of the iPhone and the Apple Watch, like “iOS 26 or later”. A guide about the iPhone whose title names the Mac, like “How to Lock Your Mac from iPhone”, needs the app on the Mac too, so it keeps both. The text of the trial links to the place to buy the app: the App Store, or Gumroad for an app that is not on the App Store. The gallery renders these components directly from app metadata.

- `@Sponsors`: the sponsors of the `sponsorTiers` frontmatter of the page, on a line of its own, like on the supporters page. A page with `sponsorTiers` must have it. It has no content.
- `@Scheduled(from: 2026-11-27, until: 2026-11-30) { … }`: content that the page shows only in a build from the first day through the last day, like the text of a sale, so it shows and goes away by itself at the nightly build. The dates are SOML dates without quotes, like in frontmatter (`DirectiveDate`), and days in UTC. Only the pages in `content/pages` can have it, but not the FAQ page, and it is an unknown directive in other content. The content is always rendered, so a mistake of its Markdown is found also while the page does not show it, and its links to other pages and sections are always checked too: the build checks the links of the Markdown of each page of `content/pages` (`additionalLinks` of `LinkValidator`), not only the links of the published page. A link to a heading in the block is a broken link while the page does not show the block. The Markdown copy of the page has it only while the page shows it. `website check` warns about a block whose last day is over, so the owner removes it, and about a day in its text, like “November 30”, that is not one of its days, as the note of a sale says the last day of the dates. With the name of a sale, like `@Scheduled(from: 2026-11-27, until: 2026-11-30, sale: "Black Friday") { … }`, the page of each paid and active app that the content links to, like `[Dato](/dato)`, shows a note on the same days (`Sale`, `AnnouncementBanner`): “Black Friday: Dato is on sale through November 30”, with a button to the page of the block, which opens it at the first “Dato” of the page with a text fragment (`LinkDestination.path(_:highlighting:)`), so the block is the first text of the page with the names of its apps. A free or archived app gets no note. So the dates and the apps of a sale are only in the block. The note has no price, no discount, and no code, as they are on the page of the sale, and it replaces the `announcement` of the app on those days. Before the first day, the page of the block shows only the name and the dates of the sale, in a tip alert with the name as its title (`ScheduledArguments.saleAnnouncement(on:)`), like “The sale runs from November 27 to November 30. The apps and the discounts show here when it starts.” (or “is on November 27” for a sale of one day), so the sentence does not repeat the name, and the Markdown copy of the page has the same sentence after the name in bold, like “**Black Friday:** The sale runs from …”. The apps of the block get no note before the first day. The Markdown copy of the app page does not have the note, and keeps the `announcement`. A link to the product of an app on Gumroad, like `https://sindresorhus.gumroad.com/l/supercharge/BLACKFRIDAY`, counts like a link to its page. `--date 2026-11-27` of `website serve`, `build`, and `check` (`SiteOptions`) builds the site as on that day, to see the block before its first day. It only changes the day of the build (`SiteContent.today`): the data from other services is of today.
- `@SocialLinks`: the social links of `Site.author` as chips with icons. The footer has the same links, as plain links. It has no content.
- `@Details(summary: "…") { … }`: a collapsible section with the look of the FAQ questions, for long details that most readers skip, like the steps for an older macOS version.
- `@QuickAnswer { … }`: the short answer at the top of a guide, in a box with a “Quick Answer” label, for readers who only want the answer.
- `@Tips { - … }`: a box of tips, with the look of a tip alert. `title` changes its title, like `@Tips(title: "Hidden features")` below a “Tips” heading.
- `@Columns { - … }`: a list of short items in columns, like the video call services of Dato, so a long list of names is not a narrow column several screens tall. Only for short items, as sentences read better in one column.
- `@Chips(label: "Feature groups") { - [Finder](#finder) }`: a list of links as chips, with the look of the section links of an app page, so the links to the groups of a long list, like “All Features” of Supercharge, read as navigation, and each chip keeps its words together. The `label` says what the links are, for screen readers. Each item must be one link (a content error). A heading that a chip links to, like `#### Finder {#finder}`, and the blocks below it, up to the next heading with its level or a lower one, are a group in a `<section>` (`ChipsArguments.linkedHeadingIDs`, `MarkdownDocument.Options.groupedHeadingIDs`), and its title stays below the site header while its group scrolls, like the topics of `/guides`.
- `@Photos { - [![…](photo.jpg)](photo.jpg) }`: a row of three small photos, each cut to 4:3 and a link to the full image, with a nested item below each as its caption, like the old photos of the about page.
- `@TinyApp(title: "…", icon: "/apps/…/icon.png", download: "…", source: "…", macOS: "15") { … }`: a small app without a page of its own, as a card with its icon, the text, a download button, and the requirement, like “Requires macOS 15 or later” for `macOS: "15"`, like on the tiny apps page. Only `title` and `download` are required. Without an icon, it shows the placeholder icon. The icons are in `public/apps/<slug>/`.
- `@LiveFact(kind: "week-number")`: a card with a fact of this moment from the browser of the visitor (`LiveFact`), like the numbers of the now page (`StatCard`), on a line of its own: the ISO 8601 week with its first and last day (`week-number`), like on the page of Week Number, or the time in UTC with the date in UTC and the time of the visitor (`utc-time`), like on the page of UTC Time. It has no content. The script sets the value and updates it each minute, so without JavaScript the card is hidden, and the Markdown copy of the page leaves it out. The week is the ISO week, and the card says so, as the Week Number app follows the calendar settings of the Mac, which a page cannot read.

A paragraph that only has bold text, like `**Highlights**` or `**More features**`, is a label for the list or text below it, without a colon, as the label already starts the block below it (`website check` warns about `**Notes:**`). The renderer gives it the `boldLabel` class (`ProseStyles.boldLabelStyle`), which adds slightly more space above than between paragraphs, so it reads as the start of a new group. This is intentional. A paragraph that has other text after the bold text, like `**macOS:** Click …`, is not a label and keeps the normal space, and so is a bold sentence that ends with a period, like a warning (`Paragraph.isBoldLabel`), but a bold question above its answer is a label. A paragraph that ends with a colon, like “Apple’s instructions:”, introduces the block below it: the renderer gives it the `leadIn` class, so steps, code, or a card right below it have only the space below the paragraph, like a list. In a list item with blank lines, like “Run this command:” above the code of a step, the paragraph gets the class too, and the block below it has the space of a paragraph above it, as the paragraph of an item has only the space of list items below it. A paragraph right below a block quote that starts with “— ”, like “— [Darius Foroux](…)”, is the source of the quote: the renderer gives it the `quoteSource` class (`ProseStyles.quoteSourceStyle`), in the small text of the source of a press quote, right below the quote. A paragraph that only has italic text, like `*Requires macOS 26 or later*`, is a side note: the renderer gives it the `sideNote` class (`ProseStyles.sideNoteStyle`), which shows it in the small, secondary text of a `:: ` line, and not in italics. A bulleted list where each item starts with inline code and has a `:: ` line, like the URL scheme of an app, is a reference: the renderer gives it the `commandList` class (`ProseStyles.commandListStyle`), so it has no bullets and no indent.

Inline, a platform badge marks a part that only works on some platforms: `^[macOS only](platform: "macOS")`.

An inline note shows more about a text in a popover when the text is clicked: `^[Spotlight](note: "The *search* of macOS. See [the FAQ](faq.md).")`. The text is an `InlineNote`, a link that wraps like the text around it, and the note is a popover at the end of the document. The note is Markdown, and its links are resolved and checked like other links. Write `"` in a note as `\"`, and a new paragraph as `\n\n`. A note cannot have headings, footnotes, or other notes (a content error), and it does not work in a short text that is shown inline, like a frontmatter field. The script of `InlineNote` finds its note by the ID in the link, as the note is at the end of the document, not in the element. Use a note, not a footnote (`[^id]`): the site shows both in a popover, but a note does not need a definition in another place.

Write a keyboard shortcut as `++Shift+Command+N++`, which becomes one `<kbd>` per key. Spell out the modifier keys (`Command`, `Option`, `Control`, `Shift`), and do not write shortcuts as plain text like “Command-N”. The page shows the glyph of a modifier key before its name, like “⌘ Command”, as the menus of macOS show only the glyphs: the glyph is only in the style of the key (`ProseStyles.modifierKeyStyle(_:)`), so a copied shortcut stays “Command+C”, and screen readers read only the name. In a table on phones, the key shows only its glyph, as a table of shortcuts is a reference, but the name stays in the HTML. The keys have their names on the keyboard of a Mac, so a glyph (`⌘`), an abbreviation (`Cmd`), or a lowercase name (`command`, `k`) in a shortcut is a build error, and `website check` warns about a modifier glyph anywhere in the text, also in inline code, but not in code blocks. A key without a name can be its glyph, like `⌫` and `◀`, which the page shows with its name for screen readers, like “Left Arrow”. The glyphs with a name are in `KeyboardKey.Glyph`, and another glyph is a build error. The plus key is `Plus`, like `++Command+Plus++`, as a `+` is a separator. Write a click with a modifier with the key as a key cap too, like `++Control++-click`, `++Option++-click`, and `++Option++-right-click`, not as plain text like “Control-click”, which `website check` warns about (not in a heading or a link text, and not in the frontmatter, where the text is plain).

Write a path of menus or settings in typographic quotes, with ` › ` between the items, like “System Settings › General › Date & Time”. The renderer makes each item an inline block with its arrow (`MarkdownTheme.menuPath(_:openingPunctuation:closingPunctuation:)`), so a line breaks only after an arrow, not inside the name of an item, and the arrows are in the color of secondary text. In a link, in the title of a collapsible section, or in the text of a note, the items of a path stay text, as the underline of a link does not go into an inline block, and only the arrows are their own elements, so they are gray too, and the underline goes on under them. A path of System Settings links to its pane, as a guide is read on the Mac that it is about, like “[System Settings › Displays](x-apple.systempreferences:com.apple.Displays-Settings.extension)”: the panes that the content can link to are the cases of `LinkDestination.SystemSettingsPane`, so add a case for a new pane, with the bundle ID of its extension in `/System/Library/ExtensionKit/Extensions`. A pane without a known ID, like “Energy”, stays plain text. `website check` warns about a path in quotes that is not a link although its pane is known (`LinkDestination.SystemSettingsPane.pathItems`, the path of each pane as the content writes it), about one path that links to two places, like with and without the anchor of its item (`?Privacy_AllFiles`), and about an item of a path that the content writes with and without “…”, like “Keyboard Shortcuts…”, the name of the button in System Settings. On a device that is not a Mac, where the link does nothing, `site.js` turns these links into text.

Write a collapsible section with `@Details`, not with raw `<details>` and `<summary>`, which are a build error.

An alert is a block quote with its marker alone on the first line, like `> [!NOTE]`, and text below it. The page shows the title of the kind in sentence case, like “Note”, like GitHub and like the titles of `@Tips`. Plain text after the marker is the title of the alert in place of the title of the kind, like `> [!NOTE] Update, October 2026`, with the same icon and color, like in Obsidian. A block quote that starts with a marker but is not an alert, like `> [!WARN]`, a title with Markdown, like `> [!NOTE] *Text*`, or a marker without text, is a content error, as the page would show the marker as text. A paragraph that starts with a marker but is not the start of a block quote, like after the `>` was lost, is a content error too.

A fenced code block in content renders as a `CodeBlock` (`Sources/Website/Components/CodeBlock.swift`), with its language and a copy button. The build highlights Swift code with the parser of Swift (`swiftCodeParts` in SiteKit), SOML code with the lexer of SOML (`somlCodeParts`), JavaScript code (`js`) with a small lexer of comments, strings, numbers, and keywords (`javaScriptCodeParts`), and shell code (`sh`, and the commands of a `console` block) with a smaller lexer of comments and strings (`shellCodeParts`), like the URL in `open 'lungo:toggle'`, each line of a `console` block gets a `$ ` prompt, and the code of other languages is plain. The bar shows the name of the language (`CodeBlock.Language.title`), like “Terminal” for `console`, “Shell” for `sh`, and “JavaScript” for `js`. The long lines of a `console` block and of a block without a language wrap, like a long URL, and code with a language scrolls. To show what a command prints, start each command of the `console` block with `$ `: the other lines are then output, in a lighter color, without a prompt, and the copy button copies only the commands, like:

```console
$ osascript -e 'id of app "Safari"'
com.apple.Safari
```

Then write the output in the block, not in a sentence below it. Limitation: with prompts, a command that continues on the next line after a `\` is not supported, as the next line is output, so write the command on one line. The removed and added lines of a `diff` block have a faint fill of their color from edge to edge of the block. A fence can name the file of the code after the language, like ```` ```swift Badge.swift ````, which the block shows at its top left, in the row of the bar. Markdown without the options of the site, like release notes, has a plain `pre`.

Use the directives when they fit, instead of raw HTML or a new directive, like `@QuickAnswer` at the top of a guide, and `@Details` for long notes in an FAQ answer. Mark a part of an app that works only on some of its platforms with a platform badge, like the actions of the Actions app (`content/apps/actions/index.md`), not with `<sup>`. A badge must be for a platform of the app, and `website check` warns about a `<sup>` with a platform and about a raw `<kbd>`, with the shortcut to write instead.

Do not indent the content of a directive that has a list, as a nested list then breaks. swift-markdown removes as many whitespace characters from each line as the first line has columns of indentation, so a tab-indented first line removes the tab of the nested items too, and the nested list becomes part of the outer list. The build checks it: `@Steps` must contain exactly one numbered list, and `@Cards`, `@Columns`, `@Chips`, `@Photos`, and `@Changelog` exactly one bulleted list (HTML comments do not count), so a split list is a content error at the line of the directive. Content of these directives that is indented more than the directive is a content error too, as the nested list is then one list with the outer list.

## Stack depth

A debug build renders each level of a page with a copy of the whole HTML value of that level on the stack, so a deep page can use most of the 512 KB stack of a thread, and a deeper one crashes. `AnyHTML` (SiteKit) erases the type of its content and renders it only when it renders, so the levels above it hold only a reference: the layout (`SiteLayout`) and `ProsePage` use it, and the 1999 page uses `GeoCitiesPage.Deferred`, which is built on it, for its parts and the content of its windows. Add one only at a part of a page that nears the stack in a debug build, like after a new deep part, not on every component: each one renders its content to a string and adds a level of its own.

## Scripts of components

A component with behavior is a custom element (`ScriptedElement`), like `CopyButton`: Swift renders all its markup in the light DOM, and its script is the class of the element, so the script only works on its own element and finds no elements on the page by an ID or a selector. Its script is the `.js` file in the `Scripts` folder next to the Swift file (`ElementScript()`), and the page gets it once. A value of the build that the script needs, like a media query or the language of the site, goes in the `config` of the element, which the script reads with `JSON.parse(this.dataset.config)`, not in the text of the script. A new `Scripts` folder also goes in the `exclude` of the Website target in `Package.swift`. The build publishes it unchanged, so the file defines its element itself: `class GeoCitiesLego extends GeoCitiesElement {` with the name of the Swift type, and `customElements.define('geo-cities-lego', GeoCitiesLego);` at the end, with the tag name of the element. It imports its base class and other scripts without a hash, like `import GeoCitiesElement from '/scripts/geocities-element.js';`, as the import map of the page adds the hash. To copy the element of a template part, use `clone()` of the base class, which gives the copy and its parts, like `const {element: row, parts} = this.clone('rowTemplate'); parts.name.textContent = name;` (or `napster.clone('resultTemplate')` in a setup function that gets the element). The elements in a template that the script fills are parts too, with `.part(Parts.name)` in the same `Parts` enum, so the script finds them by name, not by a tag or a position, like `querySelector('span')` or `children[1]`. `this.parts` does not have them, as the content of a template is not in the element, and a test checks that a script reads them only in a copy. For a template that is one element, like a `<span>`, `cloneTemplate(template)` is enough, which `/scripts/scripted-element.js` and `/scripts/geocities-element.js` export, like `import GeoCitiesElement, {cloneTemplate} from '/scripts/geocities-element.js';`. A page script, or an element that extends `HTMLElement`, imports it from `/scripts/dom.js`, which has the small DOM helpers without the base class, like `parts(this)` for the parts of the element, like `const {value, detail} = parts(this);`, `finePointer` for a precise pointer that can hover, `elementForFragment(hash)` for the element that a URL fragment points to, `scriptData(id)` for the data of a `JSONScript`, and `copy(text, element)`, which copies a text and says “Copied” to screen readers, for the copy button and the links of the sections. There is no list of the elements: the build finds the scripts in the `Scripts` folders, and the tests check the scripts against the elements that the pages show, so show a new element in the gallery (`GalleryPage`) when the pages only show it with data. An element that needs none of the helpers of the `ScriptedElement` base class extends `HTMLElement`, so the page does not load the base class. An element that only adds behavior to the element inside it, like a button, has `display: contents` as its root style. Another script changes an element through its attributes, as an attribute also works before the element is defined.

Behavior of a whole page, like the nebula of the home page or the filter of the apps page, stays a page script in `public/scripts`.

## Script hooks

A page script, or a script that must find elements outside its component, finds them by hooks: IDs and data attributes. A component declares the IDs that its script uses as a nested `enum IDs: String, ScriptIDSet`, and the data attributes as a nested `enum Hooks: String, ScriptDataAttributeSet`, next to its `Styles`. An ID is used like `.id(IDs.restart)`, `.popoverTarget(_:)`, or `JSONScript(id:)`, and `IDs.restart.id` refers to it, like in `.for(_:)` or an inline script. A data attribute is used like `.hook(Hooks.theme, value: "bondi")` or `.when(Hooks.theme) { … }`, and its raw value is the name after `data-`, like `mac-theme` for `data-mac-theme`, as `attributeName` adds the `data-`. The two kinds are different types, so using one as the other does not compile. A hook of one component that another file needs is used from its enum, like `AppHero.IDs.hero`. A test checks that every hook is used by a script, and that every ID and data attribute a script uses is declared as that kind. The names of form fields that a script reads, like the radio buttons of Winter Games and the message and the email of the feedback form, are neither, so they are a plain `enum FieldNames: String`.

## States

A script shows a state of an element to the styles with `data-state`, like `button.dataset.state = 'copied'`. The component declares its states as a nested `enum States: String, ElementStateSet` (SiteKit), next to its `Parts`, and the name of a case is the state, like `case copied`, or a state with a hyphen has a raw value, like `case signingOn = "signing-on"`. Its styles use them like `.when(States.copied) { … }`, or `.when(ancestorHas: States.copied) { … }` for an element inside, and Swift renders a first state with `.state(States.copied)`. A component that is not a custom element, but that a page script sets states on, declares its states the same way, like the 1999 page for `geocities.js`. Tests check that every state that the script of an element sets is one of its states, that each state is set and styled, and that the page scripts only set states that some component declares (a page script is not tied to one component).

Do not copy an ARIA state or the state of a form control to `data-state`. Style it directly, so the look always matches what screen readers say: `.pressed { … }` for a toggle button (`aria-pressed="true"`), `.expanded { … }` for a button that opens a menu (`aria-expanded="true"`), and `.current { … }` for the current item of a set (`aria-current`). For the element around it, use `.descendantPressed { … }`, like a box around a toggle button, or `.descendantChecked { … }`, like the label of a hidden radio button, and for an element inside it, `.ancestorPressed { … }` or `.ancestorCurrent { … }`. The script only sets the ARIA attribute (a form control needs no script), and Swift renders the first value, like `.ariaPressed(index == 0)` or `.attributes(.checked, when: …)`.

## Heading IDs

A heading gets a custom ID with `{#id}` at its end, like `## Scripting {#scripting}`. The ID has only ASCII letters, digits, underscores, and hyphens, so a copied link has no percent-encoded characters, and an invalid one, like `{#with gifski}` or `{#what-does-ⓘ-mean}`, is a content error that names the character. Code reads a parsed heading with `heading.title` and `heading.customID`, and makes a heading with an ID with `Markdown.Heading(level:_:id:)`, never by writing or matching `{#…}` text. The headings of an app page that the build adds or finds, like the FAQ section and the feedback question, are the cases of `App.Section` (`App+GeneratedSections.swift`), and code finds them by their IDs, not by their titles.

## Warnings

`website check` prints the warnings: possible mistakes that do not fail the build. A `Warning` has a kind (`Warning.Kind`, a static member like `.vagueLinkText`, declared next to the code that finds it) and a location (`.file(url, line:)` or `.page(path)`), and the output ends with the number of each kind. A page of the sitemap that no other page links to is a warning (`.unlinkedPage`), so a page that loses its last link does not stay in the sitemap unseen. `website check content/apps/dato` prints only the warnings of the files at the paths, or of the pages, like `/dato` or `https://sindresorhus.com/dato` (a warning of a page counts for the content file of the page, a line and a column after a path are ignored, like in `content/apps/dato/index.md:12:3`, and a path that does not exist is an error before the build, `CheckTarget`), and `--changed` only the ones of the files that git lists as changed or new. Then `--strict` counts only the printed warnings. A problem at a frontmatter key is `file.warning(.kind, at: Frontmatter.CodingKeys.key, "…")`, or `file.error(at:_:)` for a content error, and `file.warning(.kind, line:_:)` or `file.error(line:_:)` at a line, so the line and the file are of the same file. Among the warnings of the text: Markdown that shows as text, like a space in `[Dato] (/dato)` or the `*` that `**text*` leaves next to italic text, a menu path that is not in one pair of typographic quotes, like `“Remind Me” › “Tomorrow Morning”` or `Settings › Events`, a line that continues the paragraph above it without a blank line, as the content is not hard-wrapped (not in a list item or a block quote, and not after a line that ends with `\`), a URL in the text that is not a link, like `https://brew.sh` in a sentence, a range of numbers with a hyphen, like “0-255”, as the page keeps a range with an en dash, like “0–255”, on one line, an HTML comment at the start of a line between two items of a list, which splits the list in two (indent it like the text of the items), a list item that starts with a bold name and a line break, like `- **Name**\`, whose description goes on the next line after `::`, and an invisible character anywhere in a content file, also in the frontmatter and in code, like a zero-width space (U+200B), a word joiner (U+2060), a soft hyphen (U+00AD), or U+FEFF from a pasted text, but not the zero-width joiner of emoji. Also a straight apostrophe in a word, like “folder's” (not in typographic quotes, which can be what a reader types), “e.g.” (write “like” or “for example”), three periods (write “…”), a sentence about the future with a full date that is over, like “Arc stops working on 22 December 2026” (`--date` shows it before the day), and a link in a list item, like in a “Mentions” list, to an article that a press quote of the same app page already links to.

## Site settings

The values of the whole site that are content, not code, are in `content/site.soml` (`SiteSettings`), so the owner changes them without Swift: the featured apps of the apps page (`featuredApps`, at most 4 slugs of active apps, which the page shows in a daily order and `llms.txt` and the Markdown copy of the apps page list in the order of the file), and the numbers that are updated by hand, like the users of the apps. It is decoded like frontmatter (`SOMLFile`), so each mistake is a content error at its line, like the slug of an app that does not exist. `hiddenReviews` has the exact titles of the reviews that no page shows, or the exact text of a review without a title, like the reviews on Gumroad (`StoreReview.hidingKey`): an empty title or a title given twice is a content error, and `website check` warns about a title that matches no review that the build got (not when it got no reviews, as Apple sometimes sends empty feeds). It is the text of the store, not the text that the page shows, which is tidied (`StoreReview.displayTitle`, `displayText`): a capital first letter, “I” for “i”, no asterisks around a word, a title without the periods at its end, like “Simply beautiful.” for “Simply beautiful”, and a title of 6 or more letters in all capital letters in sentence case, like “NEVER MISS A MEETING AGAIN” for “Never miss a meeting again”.

The projects of the open source page are in `content/open-source.soml` (`OpenSourceCatalog`), decoded the same way: one key for each group, which is the ID of its section, like `command-line-tools`, in the order of the page by convention (the page takes the order from the cases of `OpenSourceProject.Group`, not from the file), with the `name`, the `repository`, the `summary`, and the `language` of each project. A group must have two or three projects, or a multiple of four, so the cards fill the rows of the grid (a content error), and `website check` warns about a project that GitHub does not agree with, like an archived repo or another language, at its line. The titles and the summaries of the groups stay in Swift (`OpenSourceProject.Group`). The npm packages of the page have their descriptions from npm, but a description that starts with a badge (`[![`) is the start of the readme, which npm uses when a package has no description, so the row has no description (`NPMStatistics`).

The Wall of Love (`/apps/reviews`) with `?app=dato` shows only the press quotes and reviews of that app (`ReviewsPage`), and its script spreads them over all the columns, so the press quotes are not all in one column.

## Frontmatter rules

Always expand objects and arrays in frontmatter over multiple lines, including nested and single-item collections. Use tab indentation, one property or item per line, and no commas. Empty containers stay `[]` and `{}`. Use the SOML formatter with `expandingContainers: true` to preserve comments, value spelling, and property order.

App, blog, and guide frontmatter put publication flags first: `isDraft`, `isUnlisted`, then `isArchived` for apps. The remaining order follows the property declarations of their frontmatter types: the formatter reads the macro-generated `CodingKeys.allCases`, so add or move a property at its editorial position rather than maintaining a second list. Renamed keys keep their wire spelling through `CodingKeys.stringValue`. Keep absent flags omitted: a flag is `true` or not there, and a `false` one, like `isDraft: false`, is a content error (`@TrueOrAbsent`). Apply the order with `swift run website format`; `website serve` also formats before each build. Builds and checks accept any property order and never format source files. Only top-level app, blog, and guide properties are reordered; nested objects and array items retain their order.

An app that downloads a model at the first launch, like Imago, has the size of the model in bytes in `downloadedModelSize`, which the Size fact shows after the sizes of the stores, like “66 MB plus the 16 GB model”.

Keep calendar dates as `SOML.Date` through models, comparisons, sorting, metadata, and feeds. Convert to `Foundation.Date` at the formatting boundary or when an API needs an instant.

A rule that the types cannot express goes in `validate(into:)` of the `@Frontmatter` type, at the key of its value (`problems.add(_:at:)`), and a nested value checks its own rules (`problems.validate(_:at:)`), so the build reports all the mistakes at once, each at its line. Prefer a type that makes the mistake impossible, like one enum for two keys that cannot both be set. A rule between the documents is in the loader (`SiteContent.resolveReferences`), like two apps with the same `appStoreID` or `setappID`. An `appStoreID` that the App Store does not know is a content error at its line, like a `releasesRepository` that does not exist on GitHub, but only when the lookup worked, so a failed request is a warning and does not stop a deploy.

## FAQ Suggestions on /feedback

The feedback page shows relevant FAQ links as the user types their message.

### Data sources

- **General FAQs**: the questions of `content/pages/apps/faq.md` that have `<!-- @faq.general -->`. The directive is only allowed on that page.
- **App-specific FAQs**: the `###` questions in the FAQ section (`## Frequently Asked Questions {#faq}`) of the selected app's markdown file (via the `?product=` URL param), without deeper headings and without the added feedback question. See `App.faqHeadings` in `Sources/Website/Content/App+Links.swift`. The section is found by its ID, `App.Section.faq`. It includes the common questions that the build adds, except the menu bar question (`App.Section.menuBarQuestion`), as its answer only links to the general question, which is suggested instead.
- **Common questions**: the build adds the questions that many apps have to the FAQ section of each app from its facts: the menu bar question for menu bar apps (`isMenuBarApp`), the free question for free apps on the App Store that are not archived, and the localization question for all apps. An app can also pick questions that only some apps have from `content/shared-questions.md` by the IDs of their headings, like `sharedQuestions: ['suggested-filenames']` for apps that save files (`App.SharedQuestions`). Each shared question is a level 3 heading with a short, clear ID, like `text-jumps`, also when it moved from an app file. Its answer is Markdown, and its directives, like `@faq.keywords`, work as in an app file. The shared questions go after the questions of the app, but a question about a problem has `<!-- @faq.first -->` (`App.SharedQuestions.First`), so it goes before them, like the menu bar question. Only the shared questions can have it. The links of the shared answers are site paths, like `/apps/faq#refund`, not relative links, as the answer is shown on the app pages. See `CommonQuestion` in `Sources/Website/Content/App+GeneratedSections.swift`. Do not write these questions in app files, unless the app needs a different answer: a question with the same text keeps its own answer and gets no added copy. A question without an answer, in an app file, in the shared questions, or in the general FAQ, is a content error.

- **Tips**: the `###` headings of the `## Tips` section of the selected app that have a custom ID (`{#id}`), like “Batch transcribe” (`#batch`) of Aiko. The section is found by its ID, `App.Section.tips`, so a section with another title needs `{#tips}`. See `App.tipHeadings` in `Sources/Website/Content/App+Links.swift`. The generic headings, like “Keyboard Shortcuts”, have no custom ID, so they stay out. Give a tip a custom ID to make the form suggest it.
- **Guides**: the published guides that have the selected app in their `apps` frontmatter, with the title without “How to”.

A tip and a guide are questions of the app for the script (`SuggestedQuestion`, with a `label`), so the matching rules below are the same for them: the same minimum of matching words, the same order, and the same limit of 4. The suggestion shows the label before the text, like “Guide: Open Files with Enter in Finder on Mac”, so the visitor knows that the link is not a FAQ answer. The `@faq.` directives also work below the heading of a tip, like `@faq.keywords` for a tip with a short heading, as a heading of one word cannot match the 2 words that a longer message needs.

`FAQSuggestions` (`Sources/Website/Components/FAQSuggestions.swift`) has all of them as JSON at the end of the page (`FAQSuggestions.Questions`, after the form, so the fields below the message do not wait for the data), and its script (`Sources/Website/Components/Scripts/FAQSuggestions.js`) reads it. `public/scripts/feedback.js` sets the `app` attribute of the element to the title of the selected app.

A link to the feedback page in the content has only the parameters of `FeedbackPage.Parameters`, and its `referrer` is one of `App.FeedbackReferrer`. `website check` warns about another parameter, like a misspelled `referrer`, and about another referrer.

### Heading metadata (`<!-- @namespace.attribute value -->`)

Any markdown heading with a `{#id}` can be annotated with directives on the lines immediately below:

```md
### The app does not show up in the menu bar {#app-not-showing-in-menu-bar}
<!-- @faq.keywords launching launch start open opening -->
<!-- @faq.platforms macOS -->
<!-- @faq.general -->
<!-- @faq.pinned 3 -->
```

- Each directive is a type that conforms to `HeadingDirective` (`Sources/SiteKit/Markdown/HeadingDirective.swift`), with its name and the type of its values. The FAQ directives are in `Sources/Website/Content/FAQDirectives.swift`, and the value is available as `heading[FAQDirectives.Keywords.self]`.
- The values are split on whitespace and decoded strictly as a list, like frontmatter. So an unknown platform is an error with its line. A directive without values is a flag (`HeadingDirectiveFlag`): check it with `heading.contains(FAQDirectives.General.self)`.
- A heading can have several directives, one per line, directly below it.
- The known directives are `FAQDirectives.all`, plus `FAQDirectives.General` on the general FAQ page (`Sources/Website/Components/MarkdownOptions.swift`), and `App.SharedQuestions.First` and `App.SharedQuestions.AnswerOf` in the shared questions (`Sources/Website/Content/App+GeneratedSections.swift`). An unknown name, invalid values, a directive given twice on one heading, or a directive that is not directly below a heading, is a content error with its line.
- The `@faq.` namespace is consumed by the feedback page, except `@faq.first`, which places a shared question on the app page, and `@faq.compares`, which the app page shows as a chip. Add a type to `FAQDirectives` for a new directive.

**`@faq.keywords`**: extra words that make a FAQ matchable by queries that don't use the same words as the heading text. Only add a keyword that a user would likely type and that is not already matched: not a word of the heading, not another form of a word of the heading (“sort” covers “sorted”, and “quits” covers “quitting”), not a stopword, and not a synonym. `website check` warns about such a keyword (`Heading.faqKeywordMistakes`). When a word pair is useful for many FAQs, add it to `SuggestedQuestion.synonyms` instead.

**`@faq.platforms`**: restricts the FAQ to apps that support at least one of these platforms. FAQs without this annotation are shown for all apps. An unknown platform is a content error.

**`@faq.general`**: suggests a question of the general FAQ for every app. Only on `content/pages/apps/faq.md`.

**`@faq.pinned <rank>`**: suggests the question before all others, when it has enough matching words (like other questions) and at least as many matching words as the best question that is not pinned. Lower ranks come first. The ranks are shared by the general FAQ and the app files. A pinned directive without one number is a content error.

**`@faq.first`**: puts a shared question before the questions of the app, instead of after them, like a question about a problem. Only `content/shared-questions.md` can have it (`App.SharedQuestions.First`). The app page knows it too, as the picked questions have it, but a question of an app file with it is a content error.

**`@faq.answer-of <id>`**: a shared question takes its answer from the question of the general FAQ with the ID, like `<!-- @faq.answer-of export-settings -->`, so the answer is in one place, and the app pages show it without a link to another page (`App.SharedQuestions.AnswerOf`). The shared question has no answer of its own. Only `content/shared-questions.md` can have it. An unknown ID, a question with its own answer too, and an answer with a link to a section, like `#refund`, which would go to the app page, are content errors.

**`@faq.compares <name>`**: the other app or feature that a question compares the app with, like `<!-- @faq.compares iStat Menus -->` below “How is this different from iStat Menus?”. The app page shows a “Compared with” row of chips after the features, with one chip for each such question of its FAQ section, which opens the answer. When the name is the title of another active app, like `<!-- @faq.compares Dato -->` below “What does Dato add?” of Menu Bar Calendar, the page of that app also has a chip, with the title of the app of the question, which opens the answer on the other page, unless it has its own question about that app. So no title text is matched. The name can have spaces. It is plain text, without Markdown, and each of its words has a letter or a digit, so a leftover, like the `-` of `--->`, is a content error. Two questions of one app page that compare with the same name, and the directive on a tip or on the general FAQ page, where no page shows a chip, are content errors. The feedback page does not use it.

### Matching

`SuggestedQuestion` (`Sources/Website/Content/SuggestedQuestion.swift`) prepares the words of each question at build time, so the script of `FAQSuggestions` only splits the message into words and scores the questions.

1. **Words**: lowercase, apostrophes removed, straight and typographic (“doesn't” and “doesn’t” are “doesnt”), words of 3 or more letters, digits, or underscores, and no stopwords (`SuggestedQuestion.stopwords`, also sent to the script). The patterns that split a text are sent to the script too (`SuggestedQuestion.WordPatterns`), so the message and the questions are split in the same way. The stopwords include “app”, “apps”, “application”, “mac”, and “macos”: almost every question has them. Use `@faq.platforms` for questions about one platform. “Menu bar” is one word, “menubar”, as its two words would match all the menu bar questions. The script also leaves the name of the selected app out of the message, as many questions of the app have it.
2. **Question words**: the words of the question text (`questionWords`). The words of `@faq.keywords`, the synonyms of all these words, and a word that ends in “s” without it, like “quit” for “quits”, are in `extraWords`. Together they are the words a message can match.
3. **Matching**: a message word matches a question word when it is another form of it: the shorter word with an ending (`s`, `es`, `ed`, `ing`, `er`, `ly`), also after a doubled last letter or without a last “e”, like “sync” and “syncing”, “quit” and “quitting”, and “freeze” and “freezing”. Two forms of one word match each other too, when they have the same stem (without one ending, a doubled last letter, and a last “e”, but with at least 3 letters), like “crashed” and “crashing”. A word with only the same start does not match, like “free” and “freezing”. The rules are in Swift (`SuggestedQuestion.isForm(_:of:)`), and the script gets their endings and stem steps (`SuggestedQuestion.WordForms`), like the patterns of the words, so the check of the keywords and the page agree.
4. **Score**: TF-IDF. Each matching message word adds `log((n+1)/(df+1))`, where `df` is the number of questions whose question words contain it. Rare words score higher.
5. **Minimum**: a question needs 2 matching words when the message has 2 or more known words (words that match any question), else 1. Pinned questions need the same number.
6. **Order**: pinned questions first, by rank, but only those with at least as many matching words as the best question that is not pinned, so a pin does not push down an exact match. Then more matching words come first, then app questions before general questions, then the higher score.
7. **Deduplication**: general FAQs with 0.6 or more Jaccard similarity to an app-specific result are removed. The first 4 are shown.

The script also shows a request for a crash report when the message contains a word that starts with “crash”, or “quit unexpectedly” (or “quits”), the text of the crash dialog of macOS, unless a crash report is in the message or attached (an `.ips` or `.crash` file). For an app on macOS in a browser on a Mac, the request has the steps to attach the reports from the file dialog: a button that opens the file dialog of the form, the shortcut to go to a folder, the folder with a copy button, and the name of the app. The chip of an attached crash report shows its app and version, and a note in amber when the report is of another app than the selected app, like Safari for Dato.

### Synonyms

**Synonyms** (e.g. `icloud` ↔ `sync`) live in `SuggestedQuestion.synonyms`. A group makes every word match the others, and a one-way synonym only matches in its direction (a question about a “broken” app matches a message about a “bug”, but not the other way around). They expand the words of the questions at build time.

Do **not** use `@faq.keywords` for synonyms: keywords are for *additional match terms specific to one FAQ*. Synonyms express a relationship between two concepts that applies across all FAQs mentioning either term.

### When a FAQ doesn't show as "related help" for a user's message

When asked to improve FAQ matching (e.g., "add to related help", "this FAQ didn't show up", "add keywords"), the fix is usually adding `@faq.keywords` to the relevant FAQ heading in the app's markdown file. Only add words that aren't already in the heading text. A general FAQ question also needs `@faq.general`.

Common causes for missing matches: (a) missing keywords/synonyms so the FAQ doesn't match enough query words, (b) weak app-specific FAQs crowd it out of the top 4 (app-specific FAQs rank above general ones at equal match count), (c) stopwords and short words are left out (e.g. "back up": "back" is a stopword, and "up" has fewer than 3 letters). Fix by adding `@faq.keywords` to the FAQ or synonyms to `SuggestedQuestion.synonyms`.
